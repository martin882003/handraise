# product-portfolio-map — Coordinate one product across repository boundaries

**Componente:** product-direction

## Observable outcome

A user can define the roles of multiple connected repositories, inspect evidence-backed cross-repository interfaces and plan one product goal as coordinated repository-local fronts whose readiness, runs, risk and drift roll up into a product portfolio.

## Confirmed context

Real products often span application, service, infrastructure and shared-library repositories. Flattening them into one graph or worktree would bypass repository adapters, locks and ownership. Product Direction can connect their intent and declared interfaces while Repository Intelligence and Planning remain repository-local and expose explicit missing context.

## ▶ Handoff

This is the final scope milestone. Depend on accepted product intent, per-repository system maps/v2 plans and transactional publication. Model product-level references and orchestration edges without creating cross-repository writes. Coordinate portfolio presentation with Client Experience and readiness aggregation with Runtime & Worktree Control.

## Checklist

- [ ] 1. Extend the accepted product brief with repository identity/role, declared interface and product-goal relationship contracts.
- [ ] 2. Normalize observed/declared cross-repository interfaces with evidence, direction, version/compatibility and uncertainty while retaining local snapshot ownership.
- [ ] 3. Let goal/front planning target multiple repositories while enforcing exactly one repository and lead component per front.
- [ ] 4. Validate cross-repository hard/coordination dependencies and compute readiness/critical path without bypassing local adapters or locks.
- [ ] 5. Represent unavailable, stale, unsupported or access-restricted repositories as explicit missing product context.
- [ ] 6. Build product-level outcome/component/front/readiness/run/risk/drift views with repository drill-down and bounded aggregation.
- [ ] 7. Publish only repository-local selected changes through each repository's transaction, with a reviewed two-phase coordination/recovery story for multi-repo plans.
- [ ] 8. Test partial failure, concurrent repository changes, mixed native/Director capabilities, offline repos, dependency cycles and portfolio scale/security.
